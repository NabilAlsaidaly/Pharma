# Preliminary request persistence

Orders owns submission and history operations, explicit HTTP validation/resources and its two persistence models. Cart owns `CartSnapshot::lockedForSubmission`; Catalog retains its existing selection reader and eligibility semantics; Identity supplies the authoritative active Customer and email. No Payments or System Console capability is added.

Submission is one retryable MySQL transaction: lock Customer, check active state, look up the Customer-scoped committed operation under lock, compare normalized fingerprint, then for a new operation validate authoritative email, lock owned Cart and compare its version, read all bounded selections, lock Catalog Products/Variants/Brands in deterministic order, then lock CartItems and verify the selection still matches. Persist one header and one bulk insert of children. Failure rolls back both. Cooperating Cart mutations already lock Customer first, so they serialize with submission. External Catalog changes are observed by locking reads, with independent-connection integration tests guarding the current-read boundary.

The fingerprint is SHA-256 over canonical currency, version and the six normalized contact fields including nullable notes. Email is deliberately excluded to allow retry after an account email change. No permanent locks, expiration, request cap or financial snapshots are introduced. Unique Customer-operation prevents duplicates. Returning before fresh Cart validation is essential for lost-response recovery.

`checkout_intents` stores UUID, Customer and Cart references, source version, operation UUID/fingerprint, currency, submitted-only status, contact/email snapshot and timestamps. `checkout_intent_items` stores parent, historical source selection UUID **without a foreign key**, Product and optional Variant identifiers, quantity, review flag and order. Product/Variant FKs restrict destructive changes; composite Variant/Product FK prevents mismatched ownership. A generated normalized variant key makes NULL selections unique. Parent-selection, parent-source and parent-order uniqueness plus quantity/review CHECK constraints enforce integrity. Cart ownership is established under lock by application code; existing Cart schema is unchanged.

No prices, totals, payment policy, payable amount, stock or reservation are stored. Requests never mutate Cart, Customers or Catalog. History queries scope by Customer, use indexed bounded pagination/eager children and do not join current Catalog. Submitted facts stay immutable after source CartItem removal or Catalog hiding. No write/status API exists.

The exception reporter for these three routes logs only exception class and request ID, suppressing default SQL bindings and stack arguments that could expose contact data. Infrastructure access logs must not capture HTTP bodies. Existing local database/cache/session infrastructure is reused; no Redis dependency is introduced.

Migration files are additive and tested only on the guarded isolated physical MySQL test database.
