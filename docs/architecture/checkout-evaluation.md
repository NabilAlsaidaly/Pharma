# Checkout evaluation foundation

Implemented Phase5A is limited to non-binding `POST /api/v1/checkout/evaluations`. Orders Application `EvaluateCheckout` requests Cart Application `CartSnapshot::complete`; Cart reads its own models and calls existing CatalogSelectionReader/CartEvaluator. Orders never queries Cart infrastructure directly. Thin controller supplies session identity and validated wire input, projects the existing success envelope. No new persistence, external adapters, repository framework or financial domain layer.

The focused Cart complete boundary keeps existing GET snapshot/pagination and all mutation behavior unchanged. It reads Cart header first, then bounded cap+1 sorted items, then bulk Catalog rows in one short non-locking MySQL transaction. Under verified REPEATABLE READ the first consistent Cart SELECT establishes the read view shared by subsequent CartItem/Product/Variant/Brand/image reads. No global isolation change or unnecessary Customer FOR UPDATE. Evaluation in an already open transaction inherits that transaction's snapshot; production request path has no outer business transaction. Future changes to READ COMMITTED would require revisiting this design.

Cap violation rejects before Catalog evaluation, rather than silently truncating. Complete evaluated arrays are detached before the transaction closes; pure decimal arithmetic/projection may run afterward without further SQL. Expected version is compared as an exact string against the snapshot version. A later commit may render evaluation stale, which is acceptable because no financial/fulfillment promise exists. Future submission must revalidate/bind atomically rather than reuse this response.

CartEvaluator's existing primary exclusion precedence is extracted into a shared method; total arithmetic semantics stay unchanged. Selected currency never converts/falls back; positive on_request lines contribute estimates but require human review. Hidden metadata never enters public Checkout projection; other Product IDs/names also are not needed by this minimal API. Existing Brick Math handles large decimal totals without floats, and Cart caps remain technical limits.

Separate process tests pause a live reader transaction after Cart header or before Catalog read, commit independent writer changes, then resume. Old header/items/price/availability must agree; next evaluation sees new commit/stale-version conflict. No exclusive reader locks block writer. Committed fixtures and actual connection IDs establish real overlap, not sequential HTTP approximation.

Ordinary session/CSRF/throttle infrastructure remains; the existing POST/write category applies. MySQL is the snapshot authority. No monetary cache, Redis, provider API, queue or notification is required. No business mutation, migration, Intent, Order, receipt, policy publication or stock reservation. PAY-001 and unresolved full Phase5 decisions remain binding/deferred; [ADR-018](../adr/ADR-018-checkout-evaluation-foundation.md) accepts only this narrow foundation.
