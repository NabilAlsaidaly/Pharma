# Preliminary Gift Requests

One active Google/Sanctum Customer submits one package, quantity1, one recipient, optional allowed occasion/sender display/message. Exact published version and positive independent chosen-currency package price are required. Original accepted package identity/name/version, component names/quantities/order/references, occasion ID/name, currency/display_price_snapshot, current account email, sender/message/recipient fields and timestamp are immutable. Request header and components have separate Gift tables. Public presentation history and images remain in the restrictive linked immutable package revision; Customer detail never joins current Catalog.

Input is an explicit allowlist, JSON objects only. Authoritative Customer ID/email, price and composition are resolved by the server; overrides are rejected. Geographic text is free; configured 6E zones/payment preparations are not active. Display price is historical information, not final/payable/shipping-inclusive price. No Cart, CheckoutIntent, stock, Payment, Order, Shipment or Notification is changed/created.

Lock graph: Customer → durable Customer-operation lookup → Package → selected Occasion (if any) → sorted Products → exact sorted Variants → sorted Brands → header/components insert. Catalog's locking physical-count read prevents stale structure after waiting. Package command graph: Owner → Owner-operation lookup → Package → sorted Occasions → Catalog same order → revisions/pointer/audit. Occasion-only write: Owner→Occasion, never Package. Review: Owner→replay→GiftRequest→review/events. Settings/identity Owner-only writers and Catalog writers do not acquire Customer/Package locks afterwards. No reverse Gift→Owner or Catalog→Gift edge. Bounded retry3 is not a substitute for expected-version checks or proof against all external DBA writers.

Fingerprint has explicit stable key order and normalized optional nulls/UUIDs/plain text, including exact reviewed revision and recipient values, excluding current account email. After authenticating and locking/rechecking active Customer, committed matching operation returns original ID/timestamp before current package/occasion/price/version/email checks. Changed payload409; different operation may create another request subject to attempt limits. Unique Customer-operation is durable final protection. Failed insert rolls back header and components; no partial review event exists.

Customer summary/list omit recipient/message/email/private notes. Owned detail exposes original facts; unknown/nonowned UUID404 have identical error shape. No update/delete/cancel endpoint. Owner list/search/metrics exclude recipient PII; identifier-only search and contact on authorized detail. Retention duration remains an operational policy, not invented legal advice.
