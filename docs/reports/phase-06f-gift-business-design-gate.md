### تفاصيل حفظ المسودة مقابل النشر

المسودة تحفظ التركيبات الموجودة عند تغير حالة الكتالوج مع عرض تحذير خاص للمالكة وإتاحة الإصلاح/الإزالة؛ لا تُحوَّل الروابط غير الصالحة إلى مكونات يدوية تلقائياً. إضافة روابط جديدة تتطلب صلاحيتها الحالية. النشر يعيد تحقق كل المكونات والصور والأسعار والمناسبات والحالة ويأخذ لقطة جديدة من نصوص العرض. تغير اسم المنتج أو صوره أو سعره بعد النشر لا يعدل النسخة المنشورة: تبقى نصوص وصور الباقة المحفوظة، مع فحص أهلية الروابط الحالية فقط. لا نسخ تلقائي لصور الكتالوج أو اعتمادها كصورة باقة؛ صور الباقة ترفعها المالكة.

الباقة unavailable قابلة للحفظ مسودة لكنها غير قابلة للنشر وفق هذا المقترح؛ لإيقاف باقة منشورة يمكن إلغاء نشرها صراحة. استعادة باقة مؤرشفة لا تنشرها. الرابط محجوز دائماً حتى أثناء الأرشفة ولا يتغير بعد الإنشاء.

## 4. قواعد تقنية لا تحتاج اعتماداً تجارياً جديداً

- فصل Gifts عن Catalog وOrders وPayments وDelivery؛ لا إدخال طلبات الهدايا في جداول Checkout القديمة. علاقات وصور ومكونات وإصدارات وطلبات ومراجعات وتدقيق خاصة بالهدايا، وليست JSON حرة كمصدر حقيقة.
- UUIDv7 للكيانات، UUIDv4/v7 للعمليات، مفاتيح خارجية مقيدة وقيود فرادة وCHECK فعلية. نسخ وأسعار سلسلة آمنة لـJavaScript؛ تاريخ غير قابل للتعديل عبر عمليات التطبيق.
- حفظ المسودة والنشر والمكونات والعلاقات يحدثان كوحدة ذرية، مع حفظ النسخة المنشورة السابقة عند تحرير مسودة. لا حذف مادي للتاريخ أو إعادة استخدام الروابط.
- هوية المالكة وحالة الجلسة وCSRF/no-store كما هي؛ تحقق نشط للعميل تحت قفله. منع الحقول المجهولة وتزوير السعر والمكونات والهوية.
- idempotency دائم في SQL: النطاق Customer+operation للطلب وOwner+operation لإجراءات الإدارة/المراجعة؛ بصمة تشمل الهدف والنسخة والقيم المطبعة. البريد الحالي خارج بصمة الطلب للسماح بإعادة المحاولة بعد تغييره. تطابق ملتزم سابق قبل فحص الأهلية الحالية؛ إعادة استخدام العملية بقيم مختلفة 409.
- معالجة GD خارج أقفال SQL، حد المصدر 5MiB و4096 لكل بعد و4194304 بكسل؛ الناتج PNG حتى 8MiB، أسماء خادم ثابتة خاصة ورفض SVG/MIME المخالف. لا جلب صور بعيدة، ولا صور مسودة في public disk. الاحتفاظ بالقديم وتعويض الملف الجديد عند فشل SQL؛ خطر ملفات يتيمة عند الانهيار موثق.
- صفحات وقراءات SQL محدودة، قوائم عامة 12 افتراضياً وحتى 48، قوائم المالكة/التاريخ 25، page حتى 1000؛ لا تحميل جميع الإصدارات لقائمة. مقترح body للعميل 16KiB، وللنماذج 256KiB دون رفع و10MiB مع صورة واحدة. حدود المحاولات توثّق وتختبر، ولا تتحول إلى سقف تجاري للطلبات.
- التفاصيل الحساسة على تفاصيل الطلب المأذونة فقط؛ لا أسماء/هواتف/عناوين/رسائل في البحث العام أو الإحصاءات أو الملخصات أو سجلات الأخطاء/التدقيق العامة. لا مدة احتفاظ قانونية مختلقة.

## 5. التحقيق المعماري وخطة الأقفال الأولية

**CONFIRMED:** تمت مراجعة ADR-001/002/005/009/014/015/016/019/020/021/022/023/024 ووثائق الحدود والكتالوج وإدارته وCart وCheckout وطلبات/مراجعة الطلبات وإعدادات ومحتوى 6E وعقود APIs ذات الصلة. يملك Gifts حالياً مجلدات فارغة فقط. **CONFIRMED:** CatalogSelectionReader الحالي يقرأ المنتجات والعدد الفيزيائي للـVariants ثم الـVariants المحددة ثم العلامات؛ يأخذ الأقفال بهذا الترتيب عندما lock=true. فرع Cart يملك فحص السعر الفردي ولا يصلح نسخه لقبول الهدايا؛ يعاد استخدام حقيقة الكتالوج مع أهلية هدايا مستقلة دون اشتراط سعر المكون. عمليات إدارة الكتالوج لا تكتسب أقفال عميل/باقة. ReviewStatus يحتوي مصفوفة 6D النقية؛ إعادة استخدام القاعدة ممكنة دون إعادة استخدام جداول مراجعات Checkout أو نسخ كتلة تنفيذ كبيرة.

الخطة التالية **PROPOSED TECHNICAL DESIGN / NEEDS VERIFICATION** قبل كتابة الأوامر:

1. طلب عميل: Customer → lookup replay → GiftPackage → المناسبات المطلوبة بترتيب UUID → Products بترتيب UUID → Variants بترتيب UUID → Brands بترتيب UUID → إدخال رأس الطلب ولقطته ومكوناته ذرّياً. لا Cart أو Owner lock في هذا المسار.
2. إدارة باقة: Owner revalidation → lookup replay → GiftPackage → مناسبات مرتبة عند الحاجة → Products/Variants/Brands بالترتيب نفسه عند تحقق النشر/الربط → الإصدار/المؤشر/التدقيق. لا اكتساب Customer/Cart locks بعد ذلك.
3. إدارة مناسبة: Owner → replay → Occasion فقط، دون الرجوع إلى قفل Package؛ عمليات الطلب/النشر تقرأ الحالة تحت القفل. هذا يمنع إضافة حافة Occasion→Package تعكس ترتيب الطلب.
4. مراجعة هدية: Owner revalidation → replay → immutable GiftRequest → review → event؛ لا أقفال Customer/Package/Catalog أو تعديل حقائق الطلب. نراجع نطاق العملية عبر الأهداف لكي لا يتحول تعارض الفرادة إلى خطأ 500.
5. إعدادات 6E تكتسب Owner→هدفها فقط؛ إدارة الهوية لا تكتسب باقات أو كتالوج. لا مسار Gift→Owner أو Catalog→Gift؛ الرسم الأولي لا يظهر دورة، لكن الإثبات السلوكي يتطلب اختبارات مستقلة فعلياً.

لا تُستخدم إعادة المحاولة بديلاً عن فحص النسخة، ولا تعتبر الخطة دليلاً على عدم حدوث deadlocks. أي تغيير في ترتيب الأقفال يستلزم تحليل الرسم مجدداً واختباره.
