# Simple delivery security

Use existing Owner provider/session/CSRF/revocation/prefix response boundary. Worker commands independently lock and revalidate persisted active Owner role and credential version before replay or write; no caller-supplied Owner identity. The Owner-X -> target-X graph is shared with Settings. Worker management acquires no Customer/Catalog/Order/Gift locks, no external calls, no new mutex/Redis. Revocation must wait for admitted commands or prevent later admission. Retries are bounded3; no universal deadlock-freedom claim.

Native forms allow only fixed fields and retain exact unsigned string versions and lowercase operation UUIDs. Durable SQL uniqueness and fingerprint prevent duplicate effects or changed same-operation payload. Actor validation precedes replay. Normal writes16KiB/60attempts per minute per Owner; GET body<=16KiB and empty only. Existing Zone write boundary remains64KiB and existing Store throttling/CSRF. Unknown queries/body fields reject. No raw HTML/controls or remote fetch; escaped Blade output and no phone auto-link/message action. No public worker API/driver login or PII projection.

Public Zone reads are explicitly selected exact published snapshots. Current preparatory/draft/private notes, archive, audit/operation metadata and worker/Customer/Gift-recipient data never enter projection. No-store headers, safe API errors/requestIDs and a sanitized delivery-specific reporter exclude SQL bindings/request content. Private errors use existing no-flash business validation view; generic Owner reporter logs exception class/requestID only. Name/phone/notes are operational PII, visible only in current private directory/edit; journal stores changed field names and fingerprints, not old content. No general database explorer.

Private name/phone searches use GET query parameters. Deployment access logs and support captures must omit or redact those query strings; the sanitized application exception reporter does not control external proxy/server logging or the Owner's browser history.

6H leaves contact validation limits and historical request/replay contracts unchanged. Valid phone format is not verified ownership; geographic labels do not prove coverage; missing fees never free. Informational publication/review completion never confirms money, reserves stock, creates an Order or dispatches a shipment. PAY-001/6I governs future commercial integration.

Local and CI tests, actual MySQL overlap, SQL constraints, focused query plans and synthetic browser evidence are reported separately. Deployment prerequisites remain separate: coordinated pending migrations after explicit permission, real Owner separately provisioned, TLS/private cookies/prefix/CORS, backups/retention and multi-node session/limiter sharing if applicable. Crash recovery/DBA tampering/physical PII retention and production capacity require operational policy; no new service is silently assumed.
