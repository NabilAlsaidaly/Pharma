# Business settings schema

Additive migration `2026_10_16_000002_create_store_configuration_and_content.php` depends on all earlier project migrations, including ManagementIdentity. Historical migrations are unchanged. Migration is exercised only on positively guarded physical sumaya_pharma_test, not development/production.

Settings has four aggregate tables: store_profiles, store_currencies, store_payment_policies, store_delivery_zones. Each has a corresponding `_revisions` table, eight tables total. Exact typed fields/limits are the [configuration catalog](../architecture/business-settings.md). No EAV key/value rows or full application JSON.

Aggregates: UUID primary key; unique nullable singleton_key (exact1/non-null for profile/currency/payment, null for zones); positive unsigned BIGINT lock_version; nullable published_version; archived_at and created/updated timestamps. Required business fields are NOT NULL; optional fields truly nullable. Composite FK(id,published_version) references the same aggregate's revision(record_id,version), RESTRICT deletion; publication cannot point to another aggregate or an absent revision. Archived aggregate must have null publication. No operational secret columns.

Revisions: own UUID, restrictive FK record_id, positive unsigned version, restrictive management Owner FK, fixed six-action enum, typed immutable snapshot columns, created_at only. Unique(record_id,version) is the history/publication identity. History is immutable through application/web commands: no update/delete endpoint. Direct trusted SQL/DBA alteration is not prevented by triggers/cryptography.

Full/deposit percentage DECIMAL(5,2) plus CHECK(full=100 or deposit>0 and<100). Application rejects floats, exponent notation, negatives/excess precision before SQL to prevent database coercion/rounding. Canonical decimal strings use exactly two decimals. Fees independent nullable DECIMAL(18,2), CHECK nonnegative, max9999999999999999.99. Null never means zero/free. Zone governorate/city whitespace identity is SHA256, unique even in archive; this is exact normalized record duplication detection, not geographic coverage/overlap adjudication.

Shared store_change_events covers fixed eight target-type enum values, stable target UUID, restrictive Owner FK, action enum, previous/new unsigned versions with increasing CHECK, unique Owner+operation UUID, canonical fingerprint64, request correlation100, created_at and bounded changed-field-name JSON. It references the aggregate/revision via fixed type+stable UUID+version; polymorphic target is application-enforced rather than a misleading cross-table FK. Actual aggregate/revision Owner FKs remain restrictive. No full request/body, secret, previous/new legal text copies or Customer facts in events. No event edit/delete endpoint.

Indexes: aggregate(archived_at,created_at,id), ordered aggregates(archived_at,sort_order,id); short deterministic se1…se8 constraint names; revision unique(record_id,version); event target/type/time/id, time/id and Owner/operation. Original Cart/Checkout/Review/Catalog/Customer schema/data remain untouched. Live public reads join the exact committed published revision; no backfill/read-time singleton creation.

Rollback drops events, each aggregate publication FK, its revisions then aggregate. This destroys historical configuration/content and needs separately approved backup/retention review. Restrictive circular references require this exact order. No down/migrate/reset is authorized on development/production; isolated DatabaseMigrations suites exercise migration sequencing and rollback.
